# Jetson 并发标定与瓶颈剖析（2026-10-16）

本目录是参数实验记录，不是论文正文。用户要求暂不写论文。
设备为 AGX Orin Developer Kit，OS 可见共享内存 32.188686336 GB（29.98 GiB）；
保持 MAXN，不改锁频、精度或软件环境。CUDA 与 CPU 共用物理 DRAM。

## 测量边界

固定 YOLO11n-OBB、4096x4096 uint16 合成输入、FP32 参数/输入；cuDNN 允许 TF32，
矩阵乘法 TF32 关闭。执行预处理、完整网络前向、预测搬至 CPU、受控 NMS 与 SRP1 编码。
网络为光学预训练模型，后处理使用固定 SAR 输出负载代理；不验证 SAR 分类精度。
三轮各 12 窗预热、64 窗计时；模式顺序轮换。双流用两个线程、两个独立模型及 CUDA 流，
按组等待完成。CPU 内部线程数为 1，不等待凑批，不做跨组流水。
有限值检查、哈希和日志不在服务计时内，因此整进程墙钟吞吐略低。

|---|---:|---:|---:|---:|
| batch1 | 37.8627 | 基准 | 4.7984 | 5.6938 |
| batch2 | 35.4897 | 6.69% | 9.5138 | 11.3120 |
| batch4 | 33.6711 | 12.45% | 18.9450 | 22.5528 |

双流三轮均超过配对串行基线 5%，正式服务区间无 swap。batch4 比双流约慢 1.1%，

双流另连续运行 301 秒，完成 546 窗，无 OOM、无测量阶段交换；折算 64 窗 33.0639 秒。

## Nsight Systems 诊断

`profile/` 各模式 12 窗预热、16 窗采样；`attention_profile/` 另用 8 窗确认层级归属。
CUDA 事件用于区分异步执行和 CPU 等待；NVTX 标记阶段，SQLite 留存内核时间线。
GPU 活动时间取区间并集，双流不能简单相加内核时间。

| 模式 | 每组网络前向 GPU 事件时间 / ms | GPU 活动占捕获墙钟 | 仅拷贝活动占墙钟 |
|---|---:|---:|---:|
| batch1 | 461.2 | 78.7% | 1.73% |
| batch2 | 875.4 | 79.5% | 2.49% |
| batch4 | 1740.8 | 82.7% | 4.51% |
| streams2 | 839.8 / worker | 77.3% | 2.07% |

双流 worker 时间包含资源竞争，不能相加作为完成时延；组吞吐仍用前面的独立标定。
batch4 的网络前向为 batch1 的 3.77 倍，主要工作随 batch 增加，并未获得四倍算力。
单片 CPU 预处理约 16.8 ms、受控后处理/编码约 75.0 ms；这些流程还有流水优化空间。
CPU `download` 区间约 440 ms，但 CUDA 事件实测下载只有约 5.5 ms，其余主要是在等
此前异步发出的前向计算，不能把 CPU 等待误当成搬运瓶颈。

层级捕获确认 `model.10.m.0.attn` 输入为 `[1,128,128,128]`，两头注意力，
N=128x128=16384。一个显式 FP32 注意力矩阵占
`2 * 16384 * 16384 * 4 = 2147483648 bytes = 2 GiB`。
该层关联内核在 8 窗中共执行 2.3441 s，占所有内核并集 3.7387 s 的 62.7%，
约占捕获墙钟的 49.6%。这是当前高分辨率代理的大计算/大内存热点，不能据此认为
所有遥感识别网络都必须使用约 5 GB 单片张量或都无法有效 batch。

Nsight 诊断保留了“可能未收全 CUDA/NVTX 事件”的告警；采样范围中每阶段的 NVTX
数量已与实测 worker 数核对一致，注意力形状、CUDA 事件时间和遥测相互佐证。
时间线比例作为近似诊断，不视为完整硬件计数器或精确的算术利用率。
未获得 SM/DRAM 吞吐计数器；此 Embedded 版不支持桌面版 `--gpu-metrics-devices`，
SoC metrics 要求 root，本次未更改权限。`tegrastats` 未输出 EMC 指标。
因此不能进一步认证热点是纯计算饱和还是 DRAM 带宽饱和。

## 频率复核

`frequency_control/` 是不带 Nsight/阶段事件的独立 64 窗复核，同时每约 100 ms 读
tegrastats 和 GPU devfreq。单片均值 0.5952 s，双流每组 1.0213 s，落在原标定量级内。
单片采样 GPU 频率均值 1300.1 MHz（1224--1300.5），双流均值 1285.6 MHz
（1020--1300.5）；存在动态频率变化，不宣称锁频。双流可见 GPU 温度最高约 57.2 C。
这些短期遥测不能代替长期热稳态、航天功率预算或在轨硬件认证。

## 后续配置依据

当前代理选用单片 0.597 s、双片组 1.056 s，取三轮和持续测试组均值中的较大者，
再向上取整至 1 ms。它是保守代表值，不是每次执行的硬实时上界；双流持续测试组
P95 为 1.0889 s。饱和吞吐约 1.89394 窗/s，64 窗连续服务 33.792 s。
地面容量假设为该饱和吞吐的 10 倍，64 窗计算 3.3792 s，不含传输、排队和聚合。

共享内存采用以下逻辑预算，不再把执行池当作独立物理显存：

| 用途 | 预算 / 十进制 GB | 依据 |
|---|---:|---|
| 系统及后台余量 | 8 | 加载前全系统不可用内存向上取整，再加 1 GB |
| 并发执行池 | 14 | `(CUDA reserved 峰值 + RSS 峰值) * 1.1` 向上取整 |
| 排队数据缓存 | 10 | 物理池减前两项后取整 |
| 剩余余量 | 0.1887 | OS 可见总量减配额 |

单片组预算为 8 GB、双片组为 14 GB；只占用一份组预算，不逐片叠加两份 8 GB。
RSS 与 CUDA 统计可能重叠，上式是有意保守的预算，不能称为精确物理占用。
系统预留含开发板后台，10 GB 缓存为设计分配，均不是真实卫星操作系统的实测需求。
10 GB 缓存大于一幅完整重叠图的 2.1475 GB 输入，但队列可接纳图数仍受结果缓存影响。

派生配置在 `../sar_compute_profile_20261016/main_config.json`，前端入口为
`../../examples/config_sar_current.yaml`。保持轨道、任务到达、图像、链路、P300 和 dt 不变。
执行器支持并发组，现有计算承诺按组计时；规划器对新假设分配仍保守逐片估算，
尚未实现完整的未来 batch 装箱。历史串行全天成绩不能移植到本配置。
FP16/TensorRT、融合注意力或更换识别算子需要重新标定，不能套用本次时间和内存。

工具及统计语义参照：[NVIDIA Nsight Systems](https://docs.nvidia.com/nsight-systems/UserGuide/index.html)、
[NVIDIA GPU 多流占用说明](https://developer.nvidia.com/blog/measuring-the-gpu-occupancy-of-multi-stream-workloads/)。
远端安装的 Ultralytics 8.3.13 `Attention.forward` 与实测形状是矩阵尺寸的直接依据。

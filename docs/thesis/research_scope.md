# 研究目标与建模约定

更新：2026-10-10。依据用户对开题背景、统一任务时限和星间中继的说明制定。本文是后续实现和实验的目标约定；表中标为待实现的内容不能当作当前系统能力。

## 1. 题目与核心问题

保留开题题目：**面向遥感图像处理的多星协同任务调度技术研究**。2026-10-10 最新约定：优先解决多源竞争、计算与回传窗口衔接的问题；若 MARL 没有额外收益，允许以专门调度策略作为主方法，不要求题目绑定强化学习。

研究对象是“图像获取 → 分片 → 分配与传输 → 星上/地面处理 → 结果回传 → 聚合交付”的完整任务。在有限计算、存储与时变通信条件下，设计开销可控的调度策略，利用多星资源缩短完整结果的交付时间。小型共享多智能体模型保留为候选实现。

核心应用假设：在预先定义的工作负载与约束范围内，多星协同相对原始图像全部下传后地面计算，能够在保持完整任务完成率的前提下降低端到端时延。算法假设：所提调度机制在明确的信息权限与协调成本下优于有竞争力的基线及文献适配方法；若加入 MARL，还需证明其超过相同机制的非学习控制。应用、机制与学习增益分别验证，不预设所有环境中均有优势。

## 2. 完成口径与目标

- 主线同时要求完整交付与时延收益。沿用完整 task 完成率优先的可靠性要求，但将相对 ground_compute 的完整任务时延作为核心应用证据，不能只报告更多完成任务。
- 2026-10-10 用户确认：按每个任务产生后相同的相对时限统计完整交付率，分母保留全部产生任务。先报告 30/60/120/240 分钟曲线，业务主时限尚需依据，不能按测试优势挑选。新评估与旧结果重算已实现；现有训练奖励和 checkpoint 选择仍采用原协议，后续需在新实验中统一。见 [指标与中继](delivery_metric_and_relay.md)。
- 2026-10-10 后续确认：结果中继作为新主模型的共同网络能力。`config_relay.yaml` 已开启缓存、中继与接触检查；多时限等权奖励和选模已接通，新开发训练见 [中继训练协议](relay_training.md)。历史角色训练仍按原协议解释。正式业务主时限与信息共享成本尚待标定。
- 时延起点为图像任务产生，终点为全部必需分片结果汇聚并完成聚合。包括分片开销、排队、原始数据传输、计算、结果传输和聚合；暂时设为零的阶段必须明确。
- 初版选定地面统一结果服务作为聚合终点，各地面站通过地面网络接入。地面聚合是建模选择，不要求结果回到源卫星。地面网络时延和聚合开销应可配置，并在两种计算模式中一致计入。
- 2026-10-09 已实现：全部 tile 到地面后，经可配置的固定地面转发与聚合延迟才算任务交付；默认均为 0，向上取整到时间步。尚未建模地面网络/聚合资源竞争，分片开销仍为 0；正式主表前需校准开销与敏感性。
- 报告相同任务轨迹上的完成率、失败与未完成数，以及共同完成任务的配对时延差、均值/P95和加速比。共同完成子集仍有选择偏差，须同时报告每个方法独有完成的任务数和全任务完成时间分布；不能让全等待策略靠少量快任务获胜。
- 时限内仍未完成的任务属于截尾观测，不冒充精确时延。固定到达区间并增加统一的有限排空期可减少仿真终点偏差，仍未完成的任务继续单独报告。已通过 `task_arrival_end_step` 与评估入口 `--drain-steps` 实现固定排空协议。

## 3. 遥感工作负载

当前模型把图像处理抽象为独立分片计算，尚未执行实际遥感网络。应选择可分片的代表性任务，说明边缘重叠、分片计算量、输出量和聚合方式；若需要全图上下文，必须表达额外依赖或明确排除。各方法保持相同处理质量和工作量。

早期开发配置为 1024 MB 原图，当前角色协议为 128 MB 原图；两者均为 8 个分片、每片结果 0.5 MB，即总输出约 4 MB。该比例可能显著有利于在轨处理，不能视为全部遥感任务的普遍参数。主实验须给出代表性依据，并对输出/输入比例、分片数、地面与星上算力比进行敏感性分析；不得靠削弱地面算力或只选高压缩输出场景制造优势。

2026-10-09 追加角色诊断：现已支持显式成像源列表和逐星算力，允许专用成像卫星与不产生任务的计算节点分工。单成像星用于最小机制案例；在当前接收后承诺执行的动作定义下，它主要只有一个有效调度主体。多智能体主实验需多个主动调度源，或另外实现计算节点的接单/资源分配等动作。轨道、算力预算与真实场景边界见 [布局诊断](orbit_architecture.md)。

当前开发协议已选择多个专用成像源共享计算节点，采用执行承诺。v2 分布按不同星数自动生成角色与算力，覆盖均匀、单源邻近组和双源共享组；各成像源使用同一小型 actor。具体划分、训练预算与测试边界见 [角色训练](role_training.md)。接单、资源分配和运行中迁移不在当前 agent 动作中。

## 4. 拓扑与信息权限

用户授权按研究需要选择并参数化合理假设。第一版候选为轨道面与面内序号构成的逻辑网格：同轨前后两个节点、相邻轨道面各一个节点，最多四个协作邻居。它是候选连接关系，不是空间中的静止平面网格，也不保证四条链路一直可用。

| 约束 | 建议建模方式 | 当前状态 |
|---|---|---|
| 邻居范围 | 可配置候选拓扑和最大邻居数；首选验证四邻居方案 | 已实现物理可见边上的双端最大度数限制；开发配置为 4，采用动态近邻匹配，尚非固定四方向网格 |
| 链路可用性 | 候选边同时满足地球无遮挡、最大距离和终端约束才可传输 | 已有距离/遮挡和可选链路数上限；终端建立与切换时间未建模 |
| 邻星轨道信息 | 已知候选邻居的带时间戳星历，可在断链期间本地传播；更新周期、时延和误差可配置 | 当前使用仿真器理想轨道，尚无信息更新误差 |
| 邻星动态负载 | 仅用收到的队列/缓存/任务进度消息，保留时间戳和缺失标志；断链后不自动刷新真值 | 当前存在无成本实时状态访问，需要收紧 |
| 预测输入 | 星间接触起止、估计容量、邻星星地窗口及任务完成后的回传余量 | 已加入当前邻星接触剩余时间/下次接触、逐站星地窗口、算力及计算剩余时间；未连接邻星尚无独立动作槽位 |
| 不可预知信息 | 禁止 actor 访问未来任务到达、未来调度动作或真实未来拥塞；容量预测明确依赖假设 | 后续增加观测边界检查 |
| 训练与执行 | critic 可用集中信息训练；星上仅运行共享的小型 actor | 已有 CTDE 框架 |

先检查星座密度与邻接关系的几何可达性，再冻结网格主场景。当前 12/24/48 星的随机布局不保证四邻居可用，不能直接为每颗星硬连四条边。保留轨道与规模多样性，但筛选标准必须基于几何与工作负载，不能基于候选模型成绩。

四连接方式在星座研究中有先例：Ayala Fernandez 等在其 Walker Delta 通信星座研究中假设同轨两条、相邻轨道面两条星间链路。这里只支持逻辑建模选择，不代表所有实际遥感星座采用该配置，也不直接沿用其星座参数。来源：[原论文，第 2.2.2 节](https://conference.sdo.esoc.esa.int/proceedings/sdc8/paper/88/SDC8-paper88.pdf)。

当前实现的预测依赖全星座星历及确定性的连接匹配规则，可解释为地面下发几何接触计划；actor 只读取当前邻居摘要。不能据此声称四邻居星历足以求解全网终端竞争，也不能声称已模拟遥测广播的带宽和时延。完整边界与开发结果见 [预测与训练记录](predictive_training.md)。

另增加 `execution_commitment` 实验开关：分片选定本地计算或传到邻星后承诺执行，不再对 READY 分片改派。该模式缩小调度空间，不支持原始分片多跳中继；适用对照统一使用该规则，收益不归为学习算法贡献。

2026-10-10 中继方向：成像轨道应服从观测任务，可与计算/中继轨道分别设计；源星不必直接联系地面，但完整数据路径必须可执行。结果星间中继、同预算结果缓存及原始分片中继后地面计算已作为可选机制实现，合成正负例与一个轨道开发案例已完成，见 [结果中继验证](result_relay.md)。当前共享规则读取全网即时链路/队列及预测星地窗口，不是四邻居局部路由，也不是 MARL 收益。成像与计算轨道分别设计、新环境训练及正式泛化实验仍待完成。短期无窗口不等于永久无窗口，需按轨道与站点几何检查。

## 5. 方法与对照

最新候选增加计算与回传容量预约：接收方的已承诺工作量进入预测，同轮接单后更新共享账本，后续请求改选或等待。首版是无信令成本的同步仲裁原型，尚非完整分布式请求/ACK 协议；实现和消融见 [预约调度](reservation_scheduling.md)。以下 MARL 设计保留为已有研究路线和可选学习组件。

候选方法采用参数共享的小型 actor，每星根据本地任务及有限邻居摘要，决策等待、本地处理、邻星卸载或地面卸载。轨道模块生成预测窗口，策略学习计算与通信的取舍，并关注最慢分片对整个任务的影响。邻居预测是可用信息，创新性取决于如何利用它与实验证据，不能单独把轨道预测称为新方法。

“小模型”的第一轮工程目标是单星 actor 不超过 100 万参数、FP32 权重约 4 MB 以内，并测量 batch=1、单线程 CPU 推理的中位数/P95时延、加载后内存与模型文件大小。该阈值是研究预算，不是星载硬件认证；critic 和优化器不随 actor 上星。实际硬件部署及遥感计算网络另行计算资源成本。

| 对照 | 需要回答的问题 |
|---|---|
| ground_compute：整图下传后计算 | 相对传统全地面处理是否加快完整交付，必须进入主表 |
| 仅地面计算的分片流水线 | 区分星上计算收益与允许分片提前处理的流水线收益；待实现，或在结论中明确限制 |
| local：源星计算后回传 | 多星调度是否优于单星在轨处理 |
| greedy/window_aware 与同预测信息的强启发式 | 学习是否比规则决策更有效 |
| IPPO/MAPPO、领域文献方法适配 | 方法设计是否优于通用学习与现有研究 |

主对照共享任务、通信、地面资源、质量要求、聚合口径及适用的信息权限。区分传统直传地面架构与允许原始数据经星间中继后地面计算的架构，不能将前者结果概括为超过所有地面计算策略。若聚合/中继或状态获取机制改变，所有适用算法统一接入。

## 6. 实施次序与验收

1. 补齐完整交付语义、ground_compute 配对主评估及工作负载参数依据；记录任务级到达与完成时间。
2. 校准可达的有限邻居拓扑，实现邻星/星间窗口与有时间戳的动态状态；对所有在线方法统一信息边界。
3. 小规模开发案例验证协同相对全地面与源星计算的收益及无收益条件，保留逐任务路径和阶段耗时。
4. 在这些案例上定位全 WAIT 的学习问题，完善可恢复训练，再进行多星座、多负载训练和独立验证选模。不能仅增加训练轮数就宣称问题解决。
5. 冻结协议，完成独立种子的正式对照、去预测/去任务级协作消融、跨规模与信息延迟测试，报告精度之外的模型开销。

验收对象是可解释、可复现的调度方法及其适用边界，学习版本另报告模型开销和独立增益。当前仍未建立满足正式主张的完整证据；原有开发结果保留为诊断记录，不重写为新的目标已经实现。

## 1. 已确认的实现约定及参数理由

| 项目 | 本轮约定 | 理由与证据属性 |
|---|---|---|
| 业务类型 | DOTA 类 RGB uint8 目标检测输入代理 | 可以连接公开的目标检测数据与原论文切片规则；DOTA 含卫星与航空影像，不称为某传感器的原始在轨码流 |
| 输入形状 | 显式配置 `width_px`、`height_px`、通道数及存储位深；用 4000 × 4000 × 3、uint8 作说明性 fixture | 4000² 位于 DOTA 原论文描述的尺寸量级；它是机械核算样例，不是已经读取的真实样本，也不是正式实验统一尺寸 |
| 模型窗口 | 1024 × 1024 像素 | DOTA 原论文及 Oriented R-CNN 均使用该尺寸；是否适合最终模型、显存和目标尺度仍需验证 |
| 候选步长 | 824 像素，名义 overlap 为 200 像素 | Oriented R-CNN 原文明确采用该配置，DOTA 官方工具也提供该例；200/1024 = 19.53125%，不能写成精确 20% |
| 压力档步长 | 512 像素，名义 overlap 为 512 像素 | DOTA 原论文使用该配置，可检验更高重复计算与通信成本；50% 重叠不是普适最优值或精度保证 |
| 边缘规则 | 要求图像宽高均不小于窗口，最后一窗向内平移并贴住边缘；任何一轴小于窗口均显式拒绝 | 对齐 DOTA 官方工具的末窗贴边思路，避免遗漏边缘；当前不建模 padding，末段实际 overlap 可能大于名义值 |
| 调度分组 | 默认把窗口索引网格中相邻 2 × 2 个窗口打包为一个 chunk；每轴分组边长可取 1、2、4 | 这是调度开销与并行度的实验设计，尚非实测最优；边缘组允许不足 2 × 2，不丢窗口、不补造额外窗口 |
| 输入传输 | 每个窗口以完整、未压缩 RGB uint8 数组作为核算载荷；组内外均不去重 | 明确计算重复字节，避免“计算按 overlap、通信按无 overlap”的不一致；压缩和缓存去重以后应作为独立方案 |
| 每窗计算成本 | 从外部算子标定或显式 fixture 提供，chunk 成本为其窗口成本之和；现有 fixture 每窗取 1 个抽象单位 | 图像维度不能推出真实推理秒数；该单位只用于验证累加关系，不是硬件吞吐标定 |
| 每窗输出 | chunk 输出为其窗口输出之和；现有 fixture 每窗取 0.040 MB | 由假设的 1000 条 OBB 记录各 40 B 推导，不含消息头；1000 是机械假设，不是实际检测数量或数据集统计。正式值仍需外部标定 |
| 整图完成 | 所有指定窗口结果到达汇聚位置，并完成统一坐标恢复、跨窗口合并和交付 | 不能把第一个窗口完成、部分窗口到达或重复覆盖的面积累计当作整图完成 |

上表保留几何核算阶段的候选与fixture。当前受控代理固定1024窗口、824步长、200像素名义overlap及2×2打包，不再扫描512 overlap。P0007/P0019分别得到6/40窗口、2/12个包。4000²、1 U/窗及0.040 MB/窗仍仅用于机械核算。没有把Sentinel-2四波段输入RGB模型，也不追认原有128 MB为实测来源。

## 2. 一手来源与能够支持的结论

1. [Xia 等，DOTA: A Large-Scale Dataset for Object Detection in Aerial Images，CVPR 2018，§4.1、§5.2](https://openaccess.thecvf.com/content_cvpr_2018/papers/Xia_DOTA_A_Large-Scale_CVPR_2018_paper.pdf)：原图约 800² 至 4000²，评估中采用 1024²、stride 512。该论文支持“带重叠检测窗口具有明确先例”，不支持任意遥感模型必须重叠 50%。
2. [Xie 等，Oriented R-CNN for Object Detection，ICCV 2021，实验设置](https://openaccess.thecvf.com/content/ICCV2021/papers/Xie_Oriented_R-CNN_for_Object_Detection_ICCV_2021_paper.pdf)：明确使用 1024²、stride 824，即相邻常规窗口重叠 200 像素。其模型精度或硬件速度不自动适用于本仿真。
3. [DOTA 官方切片工具，固定版本 `99388551054be9a6dabb01c8bb2a7eb562d57b4f`](https://github.com/CAPTAIN-WHU/DOTA_devkit/blob/99388551054be9a6dabb01c8bb2a7eb562d57b4f/ImgSplit_multi_process.py)：构造函数使用 `gap=512`、`subsize=1024`，文件末示例改为 `gap=200`；`slide=subsize-gap`，末窗起点设为 `max(size-subsize, 0)`。这说明官方工具也允许不同 overlap。本文借鉴其坐标规则，不声称逐行复现其训练标签截断与图像写盘实现。
4. [DOTA 官方结果合并工具，同一固定版本](https://github.com/CAPTAIN-WHU/DOTA_devkit/blob/99388551054be9a6dabb01c8bb2a7eb562d57b4f/ResultMerge_multi_process.py)：把子图坐标恢复到原图后执行按类别的 polygon NMS，示例合并 IoU 阈值为 0.1。0.1 是该工具参数，不是所有检测器应采用的通用阈值；最终阈值与 score 过滤策略需随模型验证后冻结。

## 3. 窗口生成和边缘处理

统一使用零起点、半开区间坐标。原图有效域为 `[0,W) × [0,H)`。当前实现使用方形窗口 `P_x=P_y=window_px` 和相同步长 `S_x=S_y=stride_px`，支持不同的原图宽高。校验要求 `0 < S <= P <= min(W,H)`；`S=P` 仅作为无重叠对照允许，实际示例仍为 `P=1024,S=824`。若图像某轴仅产生一个窗口，则该轴不存在相邻窗口，不能虚构重复量。

单轴末窗贴边算法：

```text
axis_starts(length, patch, stride):
    require 0 < stride <= patch <= length
    last = length - patch
    starts = [0, stride, 2*stride, ...] 中所有 <= last 的值
    if starts[-1] != last:
        append last
    return starts
```

二维窗口为两轴起点的笛卡尔积，固定行列索引确定身份。仿真manifest以 `windows_xyxy` 保存包内窗口半开边界，模型为 `overlapping_window_packets_v1`；真实像素和检测记录由独立benchmark产生。窗口ID与坐标独立于chunk分组。当前没有图像缩放，多尺度额外窗口必须另入manifest。

贴边规则保证所有已接受输入的窗口范围均落在原图内，无需补零。任何一轴小于窗口时，`ImageTiling` 明确报错 `padding is not modeled`。因此当前不能声称支持 DOTA 中所有小图，也不能静默缩放、补零或丢弃这类样本。未来支持 padding 前必须明确填充值、有效范围、由哪一端填充、是否传输补零字节及其质量影响，并更新数据流版本和测试。

对 `length>patch`，单轴窗口数为 `1+ceil((length-patch)/stride)`。相邻实际重叠宽度为 `patch-(start[k+1]-start[k])`；最后一段可能大于配置中的名义 overlap。这不是异常，也不能强行把最后一窗移回常规步长导致边缘遗漏。

## 4. 4000² RGB 样例的精确核算

约定 `MB=10^6 B`、`MiB=2^20 B`、`Mb=10^6 bit`。原图数组为 `4000*4000*3=48,000,000 B=48 MB`，约 45.776367 MiB。每个完整窗口为 `1024*1024*3=3,145,728 B=3.145728 MB=3 MiB`。

| 项目 | overlap 200 / stride 824 | overlap 512 / stride 512 |
|---|---|---|
| 单轴起点 | 0、824、1648、2472、2976 | 0、512、1024、1536、2048、2560、2976 |
| 最后相邻窗口实际 overlap | 520 像素 | 608 像素 |
| 二维窗口数 | 5 × 5 = 25 | 7 × 7 = 49 |
| 独立完整窗口载荷总量 | 78,643,200 B = 78.6432 MB = 75 MiB | 154,140,672 B = 154.140672 MB = 147 MiB |
| 相对原图有效像素/字节的重复倍数 | 1.6384 | 3.211264 |
| 2 × 2 窗口分组后的 chunk 数 | 9 | 16 |
| chunk 的窗口数分布 | 4 个含 4 窗口，4 个含 2 窗口，1 个含 1 窗口 | 9 个含 4 窗口，6 个含 2 窗口，1 个含 1 窗口 |

这里“载荷总量”表示所有窗口各传一份的字节账本，不是某次仿真的实际链路流量。源星本地处理无需对应的星间输入传输，多跳转发则会在不同链路上重复计费；失败重传也另计。原图有效数据始终是 48 MB，不能把 78.6432 MB 重新归一为 48 MB，也不能把它改称原图文件大小。

实际图像的尺寸不必等于 4000²。例如 4096² 输入在 512 步长下恰好得到 49 个无补边窗口，重复倍数为 `49/16=3.0625`；与本表 4000² 的 3.211264 不同，不能混用。小于 1024 的真实图幅在当前示例窗口下被拒绝，尚不能纳入该模式的完整数据集实验。

## 5. 模型 patch 与调度 chunk

先生成固定窗口列表，再根据窗口索引网格分组。分组绝不重新切图、重新生成 halo 或更改窗口起点。设窗口网格为 `n_y × n_x`，分组边长为 `g_y,g_x`，则 chunk 数为 `ceil(n_y/g_y)*ceil(n_x/g_x)`；每个窗口恰好属于一个 chunk。

默认 `g_y=g_x=2`；参数 1/2/4 指每轴窗口数，不是“一个 chunk 总共 1/2/4 个窗口”。固定 overlap=200 的 4000² 样例：

| 每轴分组边长 g | chunk 数 | 每组窗口数，按行优先 | 窗口总数 | 窗口输入总量 |
|---:|---:|---|---:|---:|
| 1 | 25 | 全部为 1 | 25 | 78.6432 MB |
| 2 | 9 | 4, 4, 2, 4, 4, 2, 2, 2, 1 | 25 | 78.6432 MB |
| 4 | 4 | 16, 4, 4, 1 | 25 | 78.6432 MB |

每个 chunk 打包各完整窗口，不把它们替换为去重后的外接矩形。若每窗服务成本为 `c_j`、输入载荷为 `b_j`、模型输出载荷为 `r_j`，则：

```text
chunk_input_bytes  = sum(b_j for j in chunk)
chunk_compute_cost = sum(c_j for j in chunk)
chunk_output_bytes = sum(r_j for j in chunk)
```

分组变化保持窗口总数、基础窗口计算成本、输入和输出载荷总量不变，变化的是可并行调度粒度及逐 chunk 的协议、启动和排队开销。若另计每 chunk 消息头或启动成本，应明确这些项会随 chunk 数变化，不能仍声称包括所有开销的总量严格守恒。每窗结果包含自己的标识，重组时不得添加或移除窗口级结果。

分组还影响离散执行和控制配额。历史 `step` 模式逐包占槽取整；新面板采用 `work_conserving`，每节点每步剩余计算预算供已就绪FIFO作业继续使用，避免每个短包浪费整步。通信及完成时间仍有dt分辨率；每星每物理决策周期最多4个候选槽位。因此分组实验还需报告时间量化和控制等待，不能仅归因为并行度。

本机测量实际采用batch=1逐窗推理，仿真按包内窗口成本线性相加。冻结执行内存0.8 GB是进程RSS量级占位，容量1 GB，不是独立显存或激活峰值。串行包内窗数变多不自动倍增执行内存；真正批推理需要另测服务和峰值。

## 6. 传输与地面基线

本轮采用“源端生成独立窗口、完整打包”的流量模型，组内和组间的重叠像素均计入各自载荷。不能一方面使用独立窗口的可自由调度性，另一方面无成本假定所有目标节点共享重叠像素缓存。

原图整图地面基线可以传输原图一次，再在地面运行同一窗口列表。因此说明性样例的整图基线输入为 48 MB，而将所有独立窗口下传时为 78.6432 MB；这是数据流架构差异，需如实报告。两者都必须执行同样的 25 个窗口、同一模型和同一全图结果合并，不能让整图基线仍使用旧八片计算总量，也不能要求它无理由重复下传原图像素。逐片地面基线则使用与分布式计算相同的 chunk 载荷与执行流程。

每次实际链路传输按该 chunk 或结果消息的实际字节推进，Mbps 换算为字节率时除以 8。应分别报告有效原图字节、窗口载荷总量、实际星间字节、实际下行字节以及重传字节。源端是否物化保存原图与所有窗口副本，也需要独立的缓存策略；几何字节账本不证明已经实现零拷贝或完备的物理内存模型。

新 `image_tiling` 模式的缓存使用十进制单位：`GB=1000 MB`，`memory_size_gb` 采用 `/1000`；旧模式仍保留 `/1024` 的历史约定。此兼容处理不修订历史结果，也不意味着可忽略两种模式的容量口径差异。示例中分片路径按 78.6432 MB 包载荷记账，整图地面路径按 48 MB 原图记账；代码没有真实分配和拷贝这些像素数组。

## 7. 检测结果的 merge 语义

真实检测和全图polygon NMS已在独立benchmark实现并测量，仿真消费派生服务与字节。固定窗内confidence=0.25、NMS IoU=0.7、max_det=300，全图按类别polygon NMS IoU=0.1；阈值不是质量最优证明。P0019/P0007固定阈值recall为56.76%/71.90%，不能据此声称满足业务精度。

1. 每个窗口运行同一冻结检测器及窗口内后处理，输出类别、置信度和 OBB 四个顶点坐标，并带 `patch_id`。无目标时仍提交该窗口的成功完成标识，不能与结果丢失混淆。
2. 本轮约定是单尺度坐标，整图坐标应为 `x_global=x_patch+x0`、`y_global=y_patch+y0`。当前不接受需补零输入；若未来支持 padding，还需设计有效区域过滤并验证。不得随意把越界 OBB 截成轴对齐矩形改变任务定义。
3. 汇聚端等待全部指定窗口的完整输出，按类别执行一次全图 polygon NMS。具体 IoU、score 阈值由模型验证冻结；DOTA 工具的 0.1 只能作为复现候选。相同分数用固定窗口 ID 与窗口内序号打破平局，确保调度到达顺序不改变结果。
4. 不因 chunk 分组不同而额外执行破坏性的 chunk 级 NMS。NMS 不能一般地假定可随意分组后等价合并，否则改变 g 会同时改变检测结果与输出量，污染调度粒度对比。
5. 结果经过坐标恢复、跨窗去重、格式写出及最终交付后才记 task 完成；任务失败或缺失窗口不得按重叠面积补成完成。缓存中的重复结果要按任务 ID、窗口 ID 和版本去重。

实测OBB1采用28 B小端消息头，加每目标40 B（8个float32顶点、1个float32置信度、1个uint32类别）；空窗也返回28 B，不含底层网络头。P0019/P0007合并前实际输出7480/15488 B。另保留 `examples/workload_overlap.json` 的1000目标×40 B=0.040 MB无消息头fixture，仅验证算术，不是实测目标密度。

合并耗时应测量 `T_merge(N_boxes, N_patches, model_postprocess)`，并区分坐标转换、polygon NMS、写出和交付。旧固定聚合 10 秒只是历史开发开销，不因本设计存在而变成已标定的真实 NMS 时间。核算 fixture 可显式给出开销占位值并验证状态流，但不作为正式实验的性能结论。

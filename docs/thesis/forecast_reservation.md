# 接触不确定性与多段回传报价

日期：2026-10-12。承接 [整图接纳实验](joint_admission.md) 已定位的两个误差，保留原方法与公共物理执行规则，新增可分离的预测组件。本轮不是 MARL 训练，也不是论文最终测试。

## 实现及假设

`sim/scheduler/reservation.py` 的 `_ForecastLedger` 基于当前广播的负载、现有轨道接触预测和最近星地窗口报价。原始数据仍只允许卸载至当前公共候选邻居；多段未来路径仅用于计算后结果的交付估计，不会通过动作绕过候选限制。

基础服务日历把已有链路积压放进实际预测接触区间，断开期间不扣减字节。新链路预约至少一个仿真步长，每段中继按步边界到达，修正连续服务报价中的过度乐观取整。

保守版在星间接触末端扣去一个 `contact_scan_s`，并使用不高于链路当前带宽与全连接范围最低带宽的服务率。后者按仿真已公开参数 `bandwidth_mbps_min / (1 + max_range_km / bandwidth_distance_scale_km)` 计算；无距离衰减时直接使用最小带宽。这是当前仿真带宽模型的保守估计，不是实测链路保证，也没有读取未来噪声随机数。最坏距离可能使近距离链路过于保守，应当由消融检验，不能假设一定提高性能。无窗口时的 greedy 回退也必须通过这一原始数据链路检查。

多段回传版在有限时域接触图上按预计到达时刻搜索，允许在中间节点等到下一次接触。标签包含节点和已使用跳数，最多使用公共 `relay_max_hops`（当前为八跳）。路径预约包含全部经过的有向星间服务区间，以及出口的星地终端和地面接收通道。相同资源账本下，提前到达可以等待后续窗口，因此可剪去不更早、且已使用更多跳的标签。

新路径估计可使用全网预测接触图，与旧 actor 的局部特征输入不同。虽然环境原本已导出这些接触信息，新增使用范围仍须披露。没有模拟完整状态广播协议、分布式握手、未来缓存占用或强制执行这些路径；共同实际路由仍可偏离报价。已有承诺结果的初始化仍按旧账本估计，没有为所有已承诺结果联合重排多段路径。每对星间连接只获得缓存提供的最近两段接触，星地仍只取最近窗口。有限时域、采样误差和实际公平带宽分配意味着本轮报价不能作为交付保证。

## 固定消融

搜索宽度统一为一，不继续增加上一轮未显示收益的 beam 宽度。

| 策略 | 新服务日历 | 保守边界与带宽 | 多段结果回传 |
|---|---|---|---|
| greedy | 否 | 否 | 原共同实际路由 |
| reservation_joint_sequential | 否 | 否 | 一跳报价 |
| reservation_calendar | 是 | 否 | 一跳报价 |
| reservation_guarded | 是 | 是 | 一跳报价 |
| reservation_multihop | 是 | 否 | 是 |
| reservation_forecast | 是 | 是 | 是 |

四个新策略构成二乘二消融，另保留旧整图策略和 greedy 作历史控制。必须分别比较 calendar→guarded、calendar→multihop，以及各单组件→forecast，不能把组合差值全部归为一个组件。

全套 122 项测试通过。新增六项覆盖短窗口拒绝与长窗口接受、未来三跳路径的时间/跳数/内存限制、逐跳预约与分支隔离、断链期间积压服务、关闭中继及回退检查，以及环境参数导出。

```bash
.venv/bin/python -m unittest discover -s tests -q
.venv/bin/python analysis/evaluate_reservation.py --workers 3 \
  --policies greedy reservation_joint_sequential reservation_calendar \
    reservation_guarded reservation_multihop reservation_forecast \
  --out-dir results/relay_forecast_reservation_reproduced
```

固定既有八场景、754 个任务，共 48 次六小时仿真。原始结果目录为 `results/relay_forecast_reservation_20261012/`。主评分继续使用任务年龄 30/60/120/240 分钟交付率的等权均值，辅助指标为四小时限制平均时延。不根据首批结果调整参数或挑选场景，不改变物理链路、实际路由、任务到达与算力预算。

|---|---:|---:|---:|

| 原整图顺序版 | 74.1218% | 753/754 | 3131.05 |

服务日历带来 0.1223 个百分点的小幅开发增益，完整交付集合不变，共同完成任务 85 个更快、28 个更慢、640 个相同；按场景为三升、三降、两持平。全局保守带宽与多段回传各自未提高平均评分，组合版退化最多。相对原整图顺序版，保守版丢失三个旧策略完成任务并新增一个，多段回传版和组合版各丢失两个并新增一个，不能用净变化掩盖失败集合变化。

因此保留服务日历候选与所有负结果，不将保守版或组合版提升为默认策略。更多未来拓扑信息并不自动产生更优决策，以下追加实验针对明确的等待分支缺口。

## 文献边界

沿未来接触搜索最早交付并考虑容量属于已有研究思路，不能独立作为本文的新贡献。Lowe 等（2023）的 Contact Graph Scheduling 联合请求分配与交付路由，并研究资源意识和接触可靠性。其原任务包含成像请求分发与采集；本文当前从已产生图像的分片处理开始，不能直接给新增策略冠以 CGS 名称。[原论文](https://doi.org/10.1016/j.adhoc.2023.103289)

本轮另核实到该研究的公开 Python 仓库，包含基于 SimPy 的网络仿真及 CGS 实现，并使用 MIT 许可：[ApSTL/cgs](https://github.com/ApSTL/cgs)。下一步文献对照可据此固定源码版本、核对原方法资源更新与路径执行方式，再写清从采集任务到计算任务的适配。本轮未导入或运行作者实现，不构成文献基线复现。

核对到的仓库版本为 `f97f0c7d66ef9ec55c46fb26ff678a23d9aba248`，算法入口包括 `src/scheduling.py`、`src/routing.py`。这是来源定位，尚未完成源码逐式核对与运行验证。

## 新增诊断：等待也是候选

四次动作与生命周期重放在 `results/relay_forecast_audit_20261012/`，报价重放可用 `analysis/audit_joint_quotes.py --policy reservation_forecast --reference-dir results/relay_forecast_reservation_20261012 --out <新文件>`。这些重放逐任务结果与相应评估一致。

uniform12_b 的 task_25 在服务日历版中时延由 3210 秒降为 380 秒，实际选择原始分片送地面计算，并非把原路径强行解释为改进。组合版则提前送往星 8，时延为 1250 秒。

uniform12_a 的 task_20 在组合版中从 3630 秒退化到 6600 秒。6050 秒的已知接触预测显示 6→5 还有 40 秒连接，快星 5 的承诺计算量为零；但原始数据候选只包含当前邻居，于是多段回传报价让本星慢算也成为可行方案，六个分片留在源星 6，另两片送星 0。最后一个结果 12610 秒下传，12640 秒整图完成。根因同时包括未比较等待后的计算机会和报价/实际路由的偏差，不能单独归为带宽保守程度。

据此把未来单跳原始数据卸载作为虚拟等待方案，与当前本地/邻星/地面计算共同比较；只有目标进入当前合法候选后才输出真实 OFFLOAD。未来任务和未来拥塞仍不可见，不使用事后已知轨迹。这一修正独立比较，不能把最初的组合负结果覆盖掉。

## 第二阶段协议：等待计算机会

现已实现 `reservation_deferred`，沿用不加保守带宽的多段回传账本，增加未来单跳原始数据目的地。预测使用当前队列负载、当前带宽及已知接触区间，虚拟未来卸载也占本轮试排容量；若被选目的地尚未进入当前合法候选，或报价必须使用下一段接触，则只输出 WAIT，并在下一轮重新报价。既有已接单分片不能撤销，不承诺按虚拟路径执行。`wait_better_contact` 与实际 `accepted` 分开统计；`task_preflight_accepted` 只表示找到了完整虚拟方案，不代表全部立即派发。

新测试验证“现在等待→连接后合法卸载”、当前链路即将结束时不能把下一段窗口直接当成当前可卸载，以及任务时限过滤。固定八场景比较 greedy、原多段回传版、等待版，共 24 次轨迹。初次批次因规划开销停止，保留在 `results/relay_deferred_reservation_20261012/`；完整重跑目录为 `results/relay_deferred_reservation_20261012_v3/`。

```bash
.venv/bin/python analysis/evaluate_reservation.py --workers 3 \
  --policies greedy reservation_multihop reservation_deferred \
  --out-dir results/relay_deferred_reservation_reproduced
```

追加泛化诊断在实现冻结后固定种子 `20261012`，从原训练分布按既有采样器取第 1--9 个新场景，覆盖 12/24/36 星与 uniform/near/shared 九种组合。任务种子 20261013--20261021，在启动时检索历史 JSON 归档未发现重叠。轨道高度、倾角、相位、每片计算量、到达率和带宽缩放均由原分布抽样，不按结果筛选。比较 greedy、日历版、等待版，共 27 次轨迹；完整重跑目录 `results/relay_deferred_fresh_20261012_v3/`，完整场景参数、代码和运行器指纹写入 `run.json`。未完成的初批和 `_v2` 均标注 STOPPED，不能作为完整面板结果。

```bash

  --fresh-seed 20261012 --fresh-count 9 \
  --policies greedy reservation_calendar reservation_deferred \

```

这些新场景来自训练分布，仅作不调参的新增诊断，不能作为论文最终独立测试集。旧八场景和新九场景应分别报告，不合并平均来掩盖泛化差异。

## 规划开销修正

等待版需要比较多个未来计算目的地，暴露了搜索开销。near24_a 前 60 步的 cProfile 诊断在原实现中约 23.1 秒，其中约 22.0 秒在决策；最多时间用于重复查询接触与链路服务。两个未完成批次因此停止，所有已完成结果保留。

随后只做等价剪枝：缓存同一账本下不变的接触参数与服务时长；已有更早完整交付报价时，不继续搜索到达更晚的节点；计算尚未完成就已经晚于当前最佳交付的目的地可跳过；宽度一的顺序试排直接提交当前最早报价，不构造随后会丢弃的其他分支。节点、窗口、带宽和预测时域没有缩减。

同一段 60 步的 cProfile 诊断降到约 5.6 秒，决策约 4.8 秒。该数据包含剖析开销且运行负载不同，不能直接宣称星载硬件获得相同加速。新增 40 个固定随机状态的对照测试，在资源逐步预约后比较剪枝前后的最优完整报价；全套 125 项测试通过。完整重跑通过 `--reference-dir` 自动核对匹配归档的逐任务结果、任务轨迹、轨道和配置；两个源码版本分别记录指纹，不能混称同一源码实验。

第一次优化后重跑（`_v2`）还暴露了归档检查的序列化问题：Python 元组保存成 JSON 数组后，直接比较内存配置会误报差异，尤其是 TLE 的行对。已改为统一 JSON 规范化后比较，未改变仿真与策略。该失败批次没有保存通过校验的案例，完整重跑使用 `_v3`，没有用前次部分结果补齐面板。

## 等待退化与后续判据

旧面板 near24_a 中，原多段回传版对 task_33 的交付时延为 970 秒，等待版为 8530 秒；near24_b 的 task_18 从 1650 秒变为 18180 秒。两个案例的等待版分别记录 8604、8575 次 `wait_better_contact`，而实际接纳均为 504 个分片。这些等待次数是逐轮逐分片动作计数，不能解释为独立任务数或直接相加为整体墙钟时延。至少可以确认，最终完整交付没有反映错过较早任务年龄时限的代价。

下一步先重放上述任务的逐轮目的地、报价、实际接触和路径，区分反复改变未来目标、源星队首阻塞、后续负载变化及报价/实际执行偏差。尚未完成这一步因果分解，不预设某一个因素已经解释全部退化。随后检验相对立即执行的等待收益阈值或等待预算，保持主指标和物理模型不变；不能因为本轮 uniform 表现较好就只保留该布局。

正式方法仍缺三项证据：与全地面及地面分片流水线控制的公平主对照；CGS 等文献方法的可核对适配；冻结候选后的未查看、多重复测试。小模型若参与候选排序或等待选择，应超过相同预测和预约机制的非学习版本，另报参数量、决策延迟及控制通信成本。本轮机制结果不能归为 MARL 优势。
